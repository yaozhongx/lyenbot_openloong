## D001：URDF 数值属性尾部空格

日期：2026-07-14

状态：已解决

### Bug 现象

Lyenbot 原始 URDF 中有少量 XML 数值属性带首尾空格。部分旧版 URDF 解析链可能无法稳定读取对应数值，存在惯量等机械参数被错误解析的风险。

### 影响

Pinocchio 动力学模型可能使用错误或缺失的机械参数；直接编辑 URDF 又违反“原始模型只读”的要求。

### 排查过程

1. 计算并记录原始 URDF SHA-256；
2. 检查 XML 属性内容；
3. 统计需要内存 trim 的属性数量，当前为 4；
4. 分别建立浮动基座和固定基座模型；
5. 检查惯量、质量矩阵和 Frame 是否可正常计算。

### 最终解决方案

`readNormalizedUrdfXml()` 读取完整 XML 后，只在内存字符串中 trim 属性首尾空格，再交给 Pinocchio；不把内容写回原文件。

### 验证结果

- 原始文件 SHA-256 实施前后相同；
- Pinocchio 成功得到 `nq=30`、`nv=29`；
- 活动关节、Frame、限制和动力学量可读取。

### 注意事项

日志 `normalized_attribute_whitespace=4` 是兼容处理计数，不代表 URDF 被修改。

## D002：初始基座高度导致足底穿地

日期：2026-07-14

状态：已解决

### Bug 现象

使用早期假设的基座高度时，Lyenbot 初始足底低于地面约 70.7 mm，仿真开始会出现强烈接触修正。

### 原因分析

旧高度来自其他机器人或人工常量，没有结合 Lyenbot 的 URDF 腿部尺寸、初始屈膝姿态和足底 Frame。

### 排查过程

1. 用 Pinocchio 构造 Lyenbot 初始关节姿态；
2. 计算左右 `left_foot_contact_point/right_foot_contact_point` 世界位置；
3. 反求使足底 `z=0` 的基座高度。

### 最终解决方案

将 Lyenbot 初始基座高度设为由正运动学得到的 `0.850693 m`，并由生成器写入 keyframe。

### 验证结果

Pinocchio 与 MuJoCo 在同一姿态下的左右足底位置误差约 `4.65e-7 m`，PD 站立通过。

## D003：MuJoCo actuator 顺序耦合

日期：2026-07-14

状态：已解决

### Bug 现象

旧接口使用 `mj_data->ctrl[i]` 输出第 `i` 个电机扭矩，默认控制数组顺序和 XML actuator 顺序完全一致。

### 风险

只要 XML actuator 排序变化，正确计算的膝、踝或手臂扭矩就可能施加到错误关节。

### 原因分析

关节反馈已经能够按名称查询，但控制输出仍保留了数字顺序假设。

### 最终解决方案

1. 按配置关节名查找 MuJoCo joint id；
2. 根据 `actuator_trnid` 查找驱动该 joint 的 actuator id；
3. 保存显式映射；
4. 输出到 `ctrl[actuatorId]`。

### 验证结果

23 个配置关节都能找到唯一 joint 和 actuator；静态名称映射检查通过。

### 剩余验证

仍需补充 23 个关节逐一小角度动态扰动测试，确认正方向和实际运动完全对应。

## D004：首帧基座线速度尖峰

日期：2026-07-14

状态：已解决

### Bug 现象

若首次读取时使用“当前基座高度减去初始化为零的旧位置”计算速度，可能产生数百米每秒的虚假线速度。

### 原因分析

旧位置缓存尚未建立，第一次差分不具备物理意义。

### 最终解决方案

首帧 `baseLinVel` 固定为零，同时保存当前 `basePos`；从第二帧开始才做位置差分。

### 验证结果

PD/WBC 启动时不再因首帧虚假速度触发异常控制。

## D005：WBC 双足站立约束漂移

日期：2026-07-14

状态：已解决

### Bug 现象

早期 WBC 能短时接管，但双脚世界位姿会缓慢漂移，约数秒后机器人跌倒。

### 原因分析

站立接触任务只有瞬时速度/加速度约束，没有在进入 WBC 时锁存足底世界位姿并持续纠正离散积分误差。

### 排查过程

1. 比较 PD 与 WBC 接管前后的足端世界坐标；
2. 检查 contact Jacobian 与任务误差；
3. 观察漂移为累积型而非单次映射跳变；
4. 在 WBC 接管时保存当前左右足底位姿作为 anchor。

### 最终解决方案

站立任务以锁存的足底世界位姿构造 `errX/derrX`，持续消除离散漂移；Lyenbot 使用较低刚度和较高阻尼的保守增益。

### 验证结果

第 3 秒 WBC 接管后持续站立 10 秒，最终 `base_z=0.848591 m`。

## D006：GUI 关闭时资源重复释放

日期：2026-07-14

状态：已解决

### Bug 现象

GUI 关闭回调和 demo 主程序都可能释放 `mjModel/mjData`，存在双重释放和退出崩溃风险。

### 原因分析

窗口/渲染资源和物理模型资源的所有权边界不清晰。

### 最终解决方案

- `UIctr` 只负责 GLFW window、MuJoCo scene/context、像素缓存和录像文件；
- demo 主程序独占 `mjModel/mjData`；
- `Close()` 只设置窗口关闭标志；
- 析构顺序保证先释放 GUI，再释放 MuJoCo model/data。

### 验证结果

GUI 相关目标编译通过；无 GUI 的 PD/WBC 回归仍通过。实际桌面环境中的关闭行为仍建议继续观察。

## D008：首步单支撑侧向失稳

日期：2026-07-14

状态：部分解决（准静态单步已解决，连续 walk 待验证）

### Bug 现象

低速 WBC 行走进入首步单脚支撑后，机器人出现明显横向失稳并触发安全停机。没有发现 NaN。

### 已排除

- URDF/Pinocchio/MuJoCo 基本维数一致；
- 23 个 joint/actuator 静态名称映射一致；
- 初始足底位姿一致；
- PD 双足站立通过；
- WBC 双足站立通过。

### 可能原因

- 支撑足完整接触约束或摩擦模型不合适；
- 双支撑向单支撑的质心转移不足；
- 足端轨迹和 Lyenbot 髋宽/足底几何不匹配；
- ankle effort 余量不足或 WBC 权重不合适；
- touch 只有标量法向力，接触信息不完整；
- 支撑足发生滑移；
- AzureLoong 遗留步态常量仍不适合 Lyenbot。

### 新增诊断证据（2026-07-15）

新增 `lyenbot_staged walk` 的 100 Hz CSV 诊断后，使用未启用 MPC 的 WBC 行走命令复现：

```bash
cd build
./lyenbot_staged walk --diagnostic=/tmp/lyenbot_walk_diagnostic.csv
```

关键时间线：

- `t=12.01 s`：进入左支撑，左右 touch 均有效；
- `t=12.85 s, phi=0.566`：右摆脚提前恢复 touch；
- `t=12.98 s`：左支撑足失去 touch，此前支撑足水平滑移约 `0.0032 m`；
- `t=13.17 s`：双脚均失去接触，右 ankle pitch 随后达到 effort limit；
- `t=13.478 s`：roll 达到 `1.00323 rad`，触发安全停机。

整个失败过程中 WBC `qp_status=0`，QP 等式残差最大约 `6.82e-13`，不等式最大违反量约 `2.42e-12`，因此可排除 QP 求解失败或约束数值违反。ankle effort 饱和发生在接触丢失之后，也不是首因。

确认存在的控制数据覆盖问题：`lyenbot_staged` 在 `enableMpc=false` 时仍每 5 ms 调用 `MPC::dataBusWrite()`；禁用态 MPC 把 `base_pos_des` 设置为当前基座位置，并把 `des_dq` 设置为当前速度，覆盖此前计算的横向支撑目标。日志中 `mpc_enabled=0`，但 `base_des_y` 持续跟随失稳后的 `base_y`，`des_dq_y` 最终达到约 `-1.61 m/s`。

禁用态 MPC 覆盖 WBC 轨迹/期望数据是原 `walk` 路径中的一个确定问题，但后续准静态测试证明它不是唯一原因。

### 准静态单步证据（2026-07-15）

新增两个不调用 GaitScheduler、FootPlacement 或 MPC 的独立模式：

```bash
cd build
./lyenbot_staged step-left --diagnostic=/tmp/lyenbot_step_left.csv
./lyenbot_staged step-right --diagnostic=/tmp/lyenbot_step_right.csv
```

两侧均完成双支撑移重心并检测到摆脚离地，但均在 touchdown 前镜像发散：

- `step-left`：右脚支撑，`t=11.547 s` 因 roll `-1.00203 rad` 停机；
- `step-right`：左脚支撑，`t=11.609 s` 因 roll `+1.00011 rad` 停机。

切换前 CoM 已位于支撑足中心附近。WBC QP 始终成功，非支撑侧 wrench 为零、支撑侧法向力约 `313 N`，侧别正确；发散初期支撑足滑移小于约 `1 mm`，ankle effort 仍有余量。基座随后向非支撑侧持续加速，接触力矩和滑移是在发散后增大。

因此 D008 已进一步收敛为 WBC 单支撑横向控制问题，不依赖前向落脚规划，也不能只用禁用态 MPC 数据覆盖解释。P0-2 测试工具已具备，验收仍未通过。

### 加速度链路与接触切换证据（2026-07-15）

CSV 进一步加入基座实际加速度、运动学任务 `ddq`、QP 修正后 `ddq` 和 QP 修正量。修复前，低优先级任务会使最终运动学 `ddq_y` 在约 `t=10.3 s` 反向，即使固定基座目标的误差仍在增大。原因是动态加权伪逆修正没有再次投影到累计零空间，现已在 `PriorityTasks::computeAll()` 修复。

零空间修复后，运动学 `ddq_y` 能持续朝固定基座目标并达到约 `±2 m/s²`，但 QP 在支撑足 roll wrench 接近约 `15 Nm` 上限后产生相反修正，实际基座仍向摆动脚侧加速。左右侧符号完全镜像。

同时发现原单步轨迹在 `t=8 s` 锁存摆脚起点，`t=10 s` 切换时会先给出毫米级向下目标并造成摆脚二次触地。改为切换瞬间重新锁存后，二次触地消失，但横向发散仍存在。再增加 2 秒双足静止保持后，切换前速度已收敛，发散仍复现，因此轨迹跳变和未等稳都不是唯一根因。

尝试将 CoM 目标从支撑足中心内偏 `20 mm` 改为足中心或内偏 `10 mm`：足中心目标在双足移重心阶段提前引发饱和，`10 mm` 也未降低单支撑冲击，均未保留。当前证据显示硬切单支撑前仍有非零摆脚载荷，下一步应显式规划双足载荷卸载。

共享零空间修复后的 Lyenbot 双足 WBC 回归仍通过：运行至 `13.001 s`，最终 `base_z=0.848603 m`，未触发安全停机。

### 足底 CoP 与实测载荷证据（2026-07-15）

从生成模型确认 Lyenbot 足底碰撞半长为 `0.08 m`、半宽为 `0.04 m`。原 WBC 的 roll/pitch 力矩使用与法向力无关的固定边界；例如 `fz=10 N`、`|tx|<=15 Nm` 等价于允许 `1.5 m` 的 CoP，明显超出足底。配置化 Lyenbot 路径现改为：

- `|tx| <= 0.04 * fz`；
- `|ty| <= 0.08 * fz`；
- 双支撑向单支撑过渡时，把未来摆脚的 `fz` 硬上限连续降至零。

旧 AzureLoong 构造路径仍保留原 22 约束行为。加入耦合 CoP 约束后，Lyenbot 双足 WBC 回归仍通过；单步中规划支撑脚 CoP 会到达约 `38~39 mm` 的横向物理边界，不能再通过增大固定力矩上限掩盖失稳。

初版诊断只汇总命名的规则 contact box，因此得到的约 `20 N` 摆脚残余载荷和支撑脚 CoP 向边界移动结论不完整。生成模型中 ankle-roll body 还保留原 URDF collision mesh；改为按足部 body 汇总全部 geom 的 `mj_contactForce()` 后，站立总法向力从错误的约 `176 N` 恢复为与模型重量一致的约 `312.3 N`。完整数据表明：

- 规划摆脚 `fz` 在单支撑切换前已降至 `0 N`；
- 切换时 MuJoCo 完整实测摆脚仍承载约 `37 N`；
- QP 计划支撑脚 CoP 已到约 `38 mm`，但完整实测 CoP 仍在足部 Frame 中心附近；
- 显式把 `Fr_ff` 支撑脚参考 CoP 设为内侧 `30 mm`，实测 CoP 仍未跟随且失败时刻不变，该试验已撤销。

继续测试固定 CoM 目标：脚中心目标即使把横移延长至 4 秒，仍在双支撑末端失稳；内偏 `10 mm`、3 秒横移加 2 秒硬卸载能稳定进入单支撑，但仍在 touchdown 前发散。最新 `step-left` 在 `t=14.525 s` 首次出现 `qp_status=-2`，当时 roll 仅 `-0.0695 rad`、pitch 仅 `-0.0077 rad`。验收 demo 现将非零 QP 状态纳入安全停止，避免继续使用旧解并把约束不可行放大成跌倒。

足部 mesh 横向范围约为 `±40.69 mm`，与规则 box 的 `±40 mm` 接近；前后范围为 `-66~+149 mm`，与以 ankle 原点居中的 `±80 mm` box 明显不同。尝试禁用 mesh、只保留 box 后，PD 阶段在 `t=2.124 s` 因 pitch 超限失败，已撤销。当前阻塞进一步收敛为：MuJoCo 复合足底接触几何、WBC 支撑多边形和完整实测 wrench 之间尚未建立一致性，不能直接进入动态轨迹调参。

稳定双支撑阶段，WBC 与完整实测左右 6D wrench 基本一致，例如每脚 `fz≈156 N`、`ty≈-6 Nm`，说明世界系方向、左右侧别和足 Frame 力矩参考点在静态条件下基本正确。切换前摆脚约 `37 N` 也可由静力关系解释：实际 CoM 位于右支撑脚内侧约 `24 mm`，双脚横向间距约 `225 mm`，预测左脚载荷约 `312×24/225≈33 N`。

为区分“中心目标不可达”与“任务切换冲击”，新增试验把 CoM 在 `8~12 s` 移到支撑脚中心，并在 `12~14 s` 保持纯 Stand、不切换 Walk。机器人仍于 `t=13.691 s` 因 pitch `-1.00277 rad` 停止，证明当前 Stand 控制不能稳定维持该中心目标。该试验已撤销，恢复内侧 `10 mm` 基线。由此形成明确矛盾：稳定可达目标必然保留约 `30~40 N` 摆脚载荷，而零静态载荷目标不可稳定保持；下一阶段必须研究带小载荷的动态接触释放。

动态释放首个候选采用两阶段竖直轨迹：前 `0.2 s` 抬高 `8 mm`，再于 `0.8 s` 内平滑升到 `25 mm`。它确实把完整实测摆脚 `fz<20/5/1 N` 的时刻从基线约 `13.21/13.28/13.29 s` 提前到 `13.08/13.12/13.13 s`，但 QP 不可行从约 `14.525 s` 提前到 `14.379 s`。因此“更快解除接触”本身不足以抑制后续横向发散，该轨迹已撤销；后续方案需同时约束离地后的 CoM/CoP 横向动态，不能只增大早期足端竖直加速度。

第二个候选在切换前 `0.5 s` 把 CoM 目标从支撑脚内侧 `10 mm` 短时推到脚中心，并在切换后短暂保持。该变化没有形成所需的支撑向初速度，反而在 `t=12.700 s` 使摆脚完整实测 `fz` 瞬时降为零，而 DataBus/WBC 仍声明双支撑。此时 QP 报告 `qp_status=0`、等式/不等式残差约 `2.18e-11/4.59e-12`，但 QP 基座横向加速度为 `+81.7 m/s²`，其余基座分量最高达到约 `2e4`，规划支撑脚 `fz≈1398 N`，实测约 `895 N`。随后测试于 `t=14.021 s` 失败，且 `airborne=0`、最大支撑足滑移约 `25 mm`。候选已撤销。该结果说明接触模式错误时，QP 数学可行并不能保证物理安全；后续必须把实测接触一致性和输出幅值纳入切换/安全策略。

验收 demo 已先补充输出幅值保护：WBC 启用后要求 QP 修正基座加速度前 6 维的无穷范数有限且不超过 `100`。WBC 站立仍正常通过至 `13.001 s`；有效单步基线现于 `t=14.522 s` 截获 `qp_status=0`、`qp_base_ddq_max=130.844` 的异常解，比原 `t=14.525 s` 的 QP 不可行早约 `3 ms`。该修改只增强安全停止，不代表 D008 已解决。

现已建立显式接触释放状态：`wbc_contact_release=true` 时 DataBus 仍声明 `DSt`，QP 保留双足 wrench 约束，WBC 运动学静态接触只锁定 `legStateNext` 指定的未来支撑脚，使摆脚可以抬起。demo 使用按足部 body 汇总的完整 wrench，要求摆脚 `fz<5 N` 连续 `20 ms` 后才切换正式单支撑。左脚测试在 `13.000~13.300 s` 保持 `DSt/release`，完整摆脚载荷由约 `37 N` 降至零，并于 `13.308 s` 确认后切换 `RSt`；固定时刻过早声明单支撑的问题已消除。

该状态机没有改善后续横向闭环：左脚仍于 `14.523 s` 截获 `qp_base_ddq_max=131.928`。释放期间 CoM 相对右支撑脚由约 `26.2 mm` 增至 `28.5 mm`，支撑脚实际 CoP 仅由中心移到约 `3.4 mm`；确认后 CoP 虽继续追到约 `31.5 mm`，CoM 已增至约 `42.8 mm` 且横向速度约 `+0.083 m/s`。因此下一阻塞是单支撑 CoP 建立速度落后于 CoM，而不是接触状态声明时刻。

右脚对称测试还揭示独立问题：在 `contact_release=false`、原双支撑路径完全恢复后，仍于 `11.294 s`、释放开始前截获 `qp_base_ddq_max=200.657`。100 Hz 记录在 `11.290 s` 尚正常，说明这是毫秒级双支撑卸载尖峰。它不是接触释放状态机回归，需要后续单独提高该时段诊断采样或在安全停止中转储瞬时 QP/任务量。

已增加失败时 1 kHz、最近 `100 ms` 的环形追踪。右脚数据将尖峰链路定位为：`left_knee_pitch_joint` 的速度索引 9 在 `PosRot` 层首先发散，`kin_ddq_9` 从 `11.280 s` 的约 `100` 增到 `11.293 s` 的 `4040.64`；`static_Contact` 层始终接近零，后续任务原样继承。同期左膝角从约 `0.041 rad` 伸直到 `-0.001 rad`，`q_des` 已越过零，而 QP 仅修正前 6 个浮动基加速度。规划支撑力从约 `239 N` 跳到 `1394 N`、QP 基座加速度升至 `200.657` 都是运动学奇异的后果，不是 QP 主动产生的根因。

曾试验在 Stand→Walk 切换时锁存当前 `rpy`，右脚反而在 `11.246 s` 以 `qp_base_ddq_max=420.178` 更早失败，已撤销。随后在单步 PVT 位置目标增加膝最小屈曲保护：`0.10 rad` 虽消除右侧尖峰，但使左侧停止提前约 `75 ms`；下调到 `0.03 rad` 后，右脚成功越过双支撑卸载并于 `13.298 s` 确认释放，直到 `14.494 s` 才进入横向发散，左脚则于 `13.301 s` 确认释放、`14.517 s` 停止，与原 `14.522 s` 基本一致。右侧独立奇异问题已消除，D008 现统一为左右单支撑 CoP/CoM 横向动态问题。

### 时序排除与关节力矩执行链证据（2026-07-16）

把最终双支撑卸载状态额外保持 1 秒、将释放从 13 秒延后到 14 秒后，`step-left` 失败时刻由 `14.517 s` 等量平移到 `15.520 s`。保持期间摆脚完整实测 `fz` 仍约 `39 N`，支撑脚实测 CoP 仅约 `2.8 mm`，CoM 相对支撑脚由约 `25.9 mm` 增至 `28.0 mm`，证明等待不会把开环计划 wrench 转化为实际载荷分配。候选已撤销。

把释放提前到 11.5 秒并与 wrench 卸载重叠后，虽然 CoM 相对支撑脚尚约 `10.6 mm`，但支撑脚实测 CoP 仍位于反方向边缘约 `-42 mm`，且摆脚承载约 `69.5 N`。释放于 `11.914 s` 确认，随后外向速度迅速增加并在 `12.847 s` 停止，比基线更差。该候选也已撤销，说明不能只按 CoM 位置提前抬脚，还必须考虑支撑脚当前 CoP 和摆脚载荷。

100 Hz CSV 现增加每关节 `tau_ff`，用于把 WBC 前馈与 PVT 反馈分开。`step-left` 的右踝 roll 在 13.0 秒具有约 `-11.74 Nm` WBC 前馈和约 `-3.83 Nm` PVT 合反馈，最终输出约 `-15.58 Nm`；PVT 不但没有抵消前馈，反而同向增加输出。但双支撑时右脚实测 `tx` 仍仅约 `-0.19 Nm`，摆脚离地后才增至约 `11.5~11.7 Nm` 并与 WBC 结果一致。

因此当前差异不是 actuator 映射或 PVT 抵消，而是双脚闭链接触下的实际载荷/力矩分配不受 `Fr_ff` 开环参考直接控制。下一步应在不改变 OpenLoong WBC 主架构的前提下，设计使用完整实测 wrench 的双支撑载荷闭环，并把摆脚载荷、支撑 CoP、CoM 位置与横向速度共同纳入释放条件；固定等待、单纯提前抬脚和继续修改固定 CoM 偏置均已缺乏依据。

### Ankle-roll 关节行程证据（2026-07-16）

新增的关节前馈诊断进一步发现，原 `step-left` 有效基线在 10~13 秒横移期间持续给出约 `-0.186~-0.189 rad` 的左右 ankle-roll 位置目标，右踝实际最低约 `-0.162 rad`；URDF 和生成 MuJoCo 模型的范围均为 `[-0.1326, 0.1326] rad`。因此原较晚的 `14.517 s` 停止时刻包含软关节限位穿透，不满足“不得超过 URDF 限位”的验收要求。

Lyenbot staged 适配层现把全部 WBC 位置目标夹紧到 URDF 范围，并在距限位 `0.02 rad` 内衰减仅会继续向外推动的 WBC 前馈。仅夹位置目标时 `step-left` 于 `14.403 s` 停止；补充前馈保护后于 `14.239 s` 停止，但右踝最低实际角由约 `-0.160 rad` 改善到约 `-0.147 rad`，越限后 PVT 输出为恢复方向。剩余穿透来自双足物理闭链和 MuJoCo 软限位，不能再由输出夹紧单独消除。

左右镜像测试结果一致：`step-left/right` 分别在 `13.306/13.303 s` 确认释放、`14.239/14.247 s` 停止；13 秒时 CoM 相对支撑脚中心均约 `46~47 mm`，已经超出 `40 mm` 足底半宽。说明在遵守 ankle-roll 行程后，当前双足横移和直立单支撑参考本身不可行，原先靠越限获得的 CoM 位置不能继续使用。

状态驱动的 Stand 脚中心预释放也未找到可行窗口：捕获点曾保持在脚中心约 `3~12 mm`，但摆脚实测载荷始终约 `45~78 N`，在任何释放条件触发前就于 `12.656 s` 出现运动学/QP 尖峰。另一个 `0.05 rad` 支撑侧躯干 roll 候选在 `11.988 s` 产生 `qp_base_ddq_max=4219.43`；卸载期提前松弛摆脚硬接触也未改善 CoM 裕量。三项均已撤销。

当前 P0-4 的首要问题应改为：在 Lyenbot ankle-roll 合法行程内设计 joint-limit-aware 的双支撑横移姿态和接触过渡，然后再做实测 wrench/CoP 闭环。继续比较越限基线的存活时刻、缩小固定姿态幅值或放宽物理限位均不能构成有效验收。

作为对照，当前原始 AzureLoong `walk_wbc` 也不是可用成功基线：实际运行中 `t=1.018 s` pitch 已超过 `1 rad`，早于 3 秒 WBC/步态接管，且足底标量传感器持续为零。因此不使用该失败数据反推 Lyenbot 轨迹。

### 关节限位任务与捕获点门控证据（2026-07-16）

为验证 joint-limit-aware 运动学能否直接阻止 ankle-roll 越限，曾在 `static_Contact` 后加入基于 URDF 上下限的高优先级等式任务。右踝进入限位保护区后，`step-left` 在 `9.726 s`、仍处于 Stand 横移阶段时出现 `qp_status=-2`，此时姿态扰动很小、此前 QP 基座加速度最大值仅约 `0.65`。把限位任务改为随侵入量连续激活的速度阻尼后仍在同一时刻失败。因此失败来自“接触硬等式 + 关节限位硬等式”的结构性不可行，不是增益突变。该任务已完全撤销。

随后验证基于线性倒立摆捕获点的释放门控。支撑脚半宽为 `40 mm`，门控使用 `5 mm` 余量，即要求 `|y_cp|<=35 mm`：

- 保持原 11~13 秒完整卸载时，13 秒捕获点约 `45 mm`，门控没有释放；但摆脚计划载荷已经降为零，双支撑等待状态仍在 `19.388 s` 出现 `qp_base_ddq_max=732.905`；
- 把支撑目标内移量从 `10 mm` 改为 `25 mm` 后仍未释放，并在 `19.297 s` 失稳，证明固定 CoM 偏置不是缺失的几毫米修正；
- 把卸载拆成“释放前最多 50%，释放后再完成 50%”后，`step-left` 能运行至 20 秒且没有安全停止，但 13 秒捕获点约 `38.4 mm`，始终未完成离地，不能视为单步通过；
- 把最早门控时刻提前到 `12.5 s` 后，捕获点处于约 `33~35 mm` 的短暂窗口，`12.501 s` 请求释放、`12.879 s` 确认实测摆脚离地并进入单支撑，但仍在 `13.728 s` 以 `qp_base_ddq_max=339.501` 停止。离地后约 `0.849 s` 的失稳时间尺度与原基线一致。

所有门控/两段卸载候选均已撤销，恢复后的 `step-left` 精确复现 `13.306 s` 确认释放、`14.239 s` 安全停止。结论是：捕获点适合做释放必要条件，两段卸载适合避免等待态自相矛盾，但二者都不能修复当前单支撑参考在 ankle-roll 合法行程内不可实现的问题。

### 姿态可行域与双侧单步验收证据（2026-07-16）

首先试验了在线一维参考投影：分别缩放 CoM-y，以及同时缩放 CoM-y 与 roll，并尝试预留 `0.02 rad` 关节软余量。左脚分别在约 `14.080/14.043/13.877 s` 停止，单支撑阶段还会出现投影不可行或 roll 累积。原因是合法单支撑姿态不在“原直立参考到零任务误差”的简单线段上，必须同时改变横移、基座高度和姿态。该在线候选已完全撤销，源码和诊断列恢复到修改前基线。

随后新增独立 headless 工具 `lyenbot_posture_feasibility_test`。它固定初始左右足世界锚点，联合扫描：

- base height：`0.73~0.85 m`，步长 `0.01 m`；
- base-y：朝支撑侧 `0~0.14 m`，步长 `0.005 m`；
- 支撑侧 roll：`0~0.40 rad`，步长 `0.01 rad`。

每侧共 `15457` 个样本，依次检查双腿 IK、URDF 腿部位置限位、双膝不小于 `0.03 rad`，以及 CoM 相对支撑脚中心不超过 `35 mm`。左/右侧分别得到 `12927` 个 IK 成功样本、`4408` 个关节合法样本和 `546/558` 个支撑合法样本。扫描轮廓显示：

- 最小 roll `0.05 rad` 虽有数学可行点，但最小腿部限位余量只有 `0.000713 rad`，没有动态裕量；
- roll `0.15 rad`、`base_z=0.84 m` 时余量约 `0.0202 rad`，CoM 仍距支撑脚中心约 `32 mm`；
- roll `0.20 rad`、`base_z=0.83 m` 时余量约 `0.0303 rad`，CoM 距中心约 `31 mm`；
- roll `0.40 rad`、`base_z=0.80 m`、base-y 约 `±0.125 m` 时，CoM 可到支撑脚中心附近。

这证明机器人在 URDF 合法行程内并非无法单支撑，真正错误是原先“保持直立、只横移 CoM”的参考生成方式。`0.15 rad` 中间候选使左脚单支撑由原不足 1 秒延长到约 `1.618 s`，但实际 CoP 最终饱和在脚边缘，仍于 `14.652 s` 停止，因此未保留。

最终单步参考在 `8~11 s` 同时平滑调整 CoM-y、base height 和支撑侧 roll，使用 `base_z=0.80 m`、roll `±0.40 rad`、支撑脚中心向中线内移 `4 mm`。摆脚确认离地后按原地竖直轨迹落回；触地改用左右复合足完整实测 `fz` 同时超过阈值并持续 `50 ms`，以排除首次冲击反弹。触地后先保持姿态 `0.5 s`，再以固定 touchdown 端点在 `3 s` 内恢复 roll、base height 和 CoM-y，恢复完成且双足有效后才累计稳定时间。

最终验证：


因此 D008 在“左右准静态原地单步”范围内已解决，P0-2/P0-4 可以完成。后续连续 walk 的迁移和验收记录见 D011。

### 后续连续行走结果

协调姿态、复合足接触、膝最小屈曲和关节动态余量已迁移到正式 walk；低速纯 WBC 在 65.001 秒内完成 12 次支撑切换，D008 的连续模式回归也已通过。详细实现和限位证据见 D011。

## D010：足底 touch 不是完整接触 wrench

日期：2026-07-14

状态：部分解决

### 现象

左右 `touch` sensor 各输出一个法向接触力标量，当前写入 `fL[2]`、`fR[2]`，供落地阈值判断。

### 后续方案

## D011：连续 walk 接触转移与关节动态余量不足

日期：2026-07-16

状态：已解决

### Bug 现象

准静态单步通过后，正式纯 WBC walk 的旧基线仍在 `13.478 s` 左右失稳；后续候选虽然能完成一至两次触地，但会在双支撑转移期间因新支撑脚失去接触而出现异常大的 QP 基座加速度。稳定跑满 40 秒的候选又只能完成 6 次支撑切换，且左 ankle-pitch 实际位置曾比 URDF 下限越界最多 `0.010266 rad`。

### 原因分析

问题由多项 Lyenbot 适配缺口叠加：

- 未启用 MPC 时仍周期调用 `MPC::dataBusWrite()`，会覆盖 joystick/步态生成的 `base_pos_des/des_dq`；
- FootPlacement 保留 AzureLoong 的后向/内向落脚偏置和 `-35 mm` 落地高度语义，且相位末端每周期累加下降量；
- contact-box 标量没有覆盖复合足全部 geom，瞬时触地后新支撑脚丢失接触时，3 秒横向 transfer 仍按时间继续；
- 40 秒总时长从 13 秒才开始走，按 `1.5 s` 摆动加 `3 s` 双支撑最多只能覆盖约 6 步；
- 仅把 PVT 位置目标夹到 URDF 边界，不能阻止 compliant joint 在落脚冲击和支撑载荷下短时穿透。

### 排查中的撤销方案

- 把 `base_vel_des` 直接桥接到 WBC `des_dq/des_delta_q`，因 `PxPy` 使用增量任务语义而在 `14.484 s` 失败，已撤销；
- 触地前增加 `50 ms` 连续确认会把第一次切换推迟到摆脚反弹阶段，退化为 `15.237 s` 停机，已撤销；
- 直接换用离线扫描的 `base_z=0.82 m、roll=0.30 rad` 而不成套迁移 base-y/CoM-y，在准备阶段 `12.491 s` 即产生 QP 加速度尖峰，已撤销。

### 最终解决方案

- 禁用 MPC 时完全跳过 MPC 计算和写回；纯 WBC 限速 `0.03 m/s`，双支撑期间暂停前向命令；
- 正式 walk 使用镜像协调 base-y/roll、`base_z=0.80 m` 和 3 秒双支撑转移；
- FootPlacement 的前向/横向偏置、落地高度、末端下降量和最大步长改为可配置，默认保留 AzureLoong，Lyenbot 显式使用 `0/-0.04/-0.010/0/0.10`；
- 以完整复合足 `fz` 驱动 GaitScheduler，并新增默认关闭的 `minimumTransferContactForce`；Lyenbot 新支撑脚低于 `5 N` 时冻结 transfer；
- 最早触地相位调整为 `0.75`，膝最小屈曲保持 `0.03 rad`；普通关节位置参考预留 `0.030 rad`，左右 ankle-pitch 预留 `0.060 rad`，并保留越限方向前馈衰减；
- walk 验收时长延长到 65 秒。

### 验证结果

## D012：连续 walk 躯干侧倾与摆脚高度质量不足

日期：2026-07-16

状态：未解决

### Bug 现象

纯 WBC `0.03 m/s` 已能完成 65 秒和 12 次支撑切换，但 GUI 中躯干需要约 `±0.40 rad` 横向侧倾，摆脚高度只有 `0.025 m`，膝关节抬升不明显。该路径是保守低速前进行走，不是原地踏步，也不代表原 AzureLoong demo 的最终步态质量。

### 原因分析

- 当前大幅 roll 是离线可行域与连续 walk 实测共同筛出的单支撑裕量，不是原 OpenLoong 步态固有要求；
- `FootPlacement` 直接生成足端位置任务，WBC 没有单独的“抬膝高度”任务，膝角由足端、基座和冗余任务共同决定；
- 原 AzureLoong `walk_wbc` 的 `stepHeight=0.12 m` 不能直接复制。Lyenbot 当前踝关节接近动态位置边界，增加摆脚高度会同步改变摆动腿 IK、落地冲击和后续支撑状态；
- 当前连续 walk 的 base-y 参考按实时支撑脚位置生成。把 touchdown 位置直接锁存为永久参考，会与落地后的实际 FootPlacement/接触修正逐步失配。

### 已排除方案

- `base_z=0.81 m、roll=0.35 rad、CoM inward=0.0254 m、base outward=-0.0125 m`：未锁存支撑脚时在 `19.782 s` 停止，锁存后仍在 `19.434 s` 停止；
- 恢复 `base_z=0.80 m、roll=0.40 rad` 但保留 touchdown-y 锁存：在 `31.449 s` 因 `qp_base_ddq_max=236.11` 停止；撤销后原基线重新完成 `65.001 s/12` 次切换；
- `stepHeight=0.050 m`：在 `61.100 s` 因 `qp_base_ddq_max=399.545` 停止；
- `stepHeight=0.040 m`：完成 65 秒，但右 ankle-pitch 有 25 个位置越界样本，最大越界 `0.001984 rad`；
- `stepHeight=0.035 m`：完成 65 秒，但左 ankle-pitch 仍有 3 个越界样本，最大越界 `0.000932 rad`；
- 将 ankle-pitch 参考余量从 `0.060 rad` 增到 `0.065/0.070 rad`：位置越界分别为 1/67 个样本，说明提前夹紧会改变闭链动力学，效果不单调；均已撤销。

### 上游 WBC 数据流恢复证据

新增只用于迁移对照的 `walk --upstream-wbc-inputs`：运动种子沿用原公式，重力前馈不照抄 AzureLoong 每脚 `370 N`，而是由 MuJoCo Lyenbot 总重 `312.327 N` 计算为每脚 `156.164 N`。保留现有 3 秒 transfer 时结果为：

仅把该模式的 transfer 从 `3.0 s` 缩短为 `1.5 s` 时，在 `19.357 s` 以 `qp_base_ddq_max=109.551` 停止，候选已撤销。结论是时序、base-y/CoM-y 和 wrench 转移必须联合迁移，不能继续单变量缩短时间。

### 2.25 秒协调换载验证

新增显式 `--coordinated-transfer`，要求同时启用 `--upstream-wbc-inputs`。该分支把 transfer 调整为 `2.25 s`，用同一余弦平滑 phase 生成 base-y、roll、诊断用 CoM-y 和双脚名义 `Fr_ff`。现有 Walk 优先级实际跟踪 base 位置而不是 `pCoMDes`，因此 CoM-y 只用于保持上游参考语义可观测，本轮没有伪造新的 CoM 控制任务。

### 摆脚竖直端点与膝屈曲诊断

当前竖直轨迹使用控制点 `[0,0,0,0,0,1,1,1]` 的 7 阶 Bezier：

```text
B(s)=21s^5-35s^6+15s^7
上升段：s=phi/0.2
下降段：s=(1.4-phi)/1.2
```

协调换载基线 16 次落脚的 touchdown phase 为 `0.743333~0.759333`。在 `phi=0.75` 时下降段 `B=0.300420`、`dB/dphi=-1.582338`，因此足端参考尚未到虚拟 `1.4` 端点且仍有下降速度。实测触地前摆脚期望 z 通常约 `-6.3~-6.6 mm`，实际足 Frame z 约 `1.2~1.6 mm`；该跟踪误差、复合足碰撞厚度和 `-10 mm` 落地偏置共同形成当前接触。

为验证能否在不提高峰值的情况下改善落地连续性，测试了峰值 phase `0.30`、平滑落地 phase `0.85`、相对支撑脚 `-6 mm` 端点、`6 mm` 有界余弦触地搜索，以及 `20/50 ms` touchdown 连续确认。结果依次暴露以下边界：

- 端点继续依赖 base-z 时，base 升至约 `0.806 m` 会把落地目标抬到约 0，第三步在 `phi=1` 无接触，并于 `23.811 s` 出现 QP 失败；
- 改为相对支撑脚 `-6 mm` 后，摆脚在 `phi=1` 的实测法向力只有 `4.29 N`，不足 `20 N` touchdown 阈值；
- 增加有界 `6 mm` 搜索后能产生瞬时触地，但进入双支撑后接触丢失，65 秒只完成 2 次切换；
- 加入 `20 ms` 确认仍会在随后双支撑丢失接触；`50 ms` 确认虽推进更多步，但在 `33.503 s` 触发 `qp_base_ddq_max=101.723` 安全停止。

上述运行时候选已全部撤销，2.25 秒协调换载重新精确通过 `65.001 s/16` 次切换。结论是当前提前触地不是单纯的曲线端点 Bug，而是摆脚跟踪、足底碰撞、接触确认与后续双支撑锚点的耦合结果；在线继续调整 phase 会把问题转移到接触状态机。

同一基线中，摆动膝实际最大屈曲 `0.576341 rad`，期望最大 `0.604845 rad`，跟踪并未缺失。Lyenbot 单腿为 6 个关节，固定 base 与 6D 摆脚姿态后没有独立膝冗余；若希望增加可见屈膝，必须联合改变足端高度/姿态或 base 参考，并同时检查 ankle-pitch 余量。下一步转为离线联合可行域扫描，不在在线 WBC 中直接叠加膝等式任务。

### 离线膝踝联合扫描与摆腿候选（2026-07-18）

`lyenbot_posture_feasibility_test` 已扩展为完整 6D 摆动足扫描。对当前 `base_z=0.80 m、roll=0.40 rad、base_y≈±0.125 m` 姿态族，左右结果严格对称：每侧 7605 个样本中 7153 个 IK 收敛、1954 个满足 URDF 腿部限位、672 个同时满足 ankle-pitch 至少 `0.060 rad` 和全腿至少 `0.015 rad` 余量。`35 mm` 高度配合约 `0.10 rad` 足 pitch 的代表解为膝屈曲 `0.673 rad`、ankle-pitch 余量 `0.337 rad`；满足余量的高度上限约为 `40 mm`。

最大等式残差 `2.132e-14`、最大不等式违反 `2.746e-12`；最小 position/velocity/effort 余量为 `0.012601 rad`、`9.65941 rad/s`、`19.7544 Nm`。15 次 touchdown 后足间距除首步 `0.2130 m` 外稳定在 `0.2072~0.2089 m`。最大实测横向加速度 `4.395 m/s²` 低于摆腿候选的 `4.567 m/s²`，但 WBC 横向 QP 加速度峰值 `0.561 m/s²` 高于其 `0.422 m/s²`，说明动态修正代价有所增加。

## D014：原 `walk_wbc` 第三次换载 QP 基座加速度突增

日期：2026-07-18

状态：部分解决

### Bug 现象

默认 StateEst 路径已完成左右各一次摆动和 2 次支撑切换，但 65 秒扩展在 `t=13.083 s`、第三次换载进入 `DSt` 后触发安全停止：`qp_status=0`，`qp_base_ddq_max=19532.767`，左右实测法向力约 `383.5/628.5 N`。

### 当前结论

- QP 返回成功码但基座加速度解异常，不能仅依赖 `qp_status` 判定有效性；
- 13 秒正式运行、13 秒真值 A/B、13 秒 stand-only 和模型一致性均通过；
- 1 kHz 扩展诊断已确认最终基座加速度最大值约 `19532.8`，但 `ddq_final_kin` 最大值仅约 `13.3`；异常由 QP 基座修正产生，不是 `PriorityTasks` 伪逆放大；
- 同一时刻 `static_Contact` Jacobian 奇异值约为 `0.139~2.68`，QP 等式残差约 `1.8e-11`、状态码为 0；双脚结果 wrench 同时逼近法向力、CoP 和 yaw 约束，因此属于声明接触模型下的极端可行解；
- 常规 DSt 中，第一次待接触脚低于 `5 N` 仅约 `12 ms`，第二次累计约 `1.679 s`。`minimumTransferContactForce` 只冻结 `transferPhi`，WBC 仍把整个 DSt 当作双脚 12D 刚性接触，这是当前明确的数据语义缺口；
- 实测接触集合在一个计划 DSt 内会经历“旧单支撑→双接触→新单支撑”。直接替换 WBC `legState` 会同时改变 `static_Contact`、`SwingLeg`、接触锚点和 wrench 约束，多个带滞回候选分别于 `12.146/13.114/11.153/12.773/12.260 s` 回归，均已撤销；
- 单边复用原 `wbc_contact_release` 可使换载相位从冻结推进至约 `0.71`，但旧支撑脚卸载后仍恢复错误的双脚约束，最终于 `13.095 s` 停止，候选已撤销；
- 三阶段接触集候选在 `12.696 s` 进入新单支撑接触语义时 QP 不可行；恢复原时间驱动换载后分别在 StateEst/真值路径的 `11.917/12.641 s` 失败；50 ms 载荷比例同步候选又在 `10.906 s` 单支撑发散。说明接触集、时间相位或实测载荷任一单项替换都不是完整解，相关代码已撤销；
- 对比 staged 正式输入路径后发现，`lyenbot_walk_wbc` 虽在 DSt 清零 `des_delta_q/des_dq/des_ddq`，但 `JoyStickInterpreter` 仍持续推进 `base_pos_des.x`。默认在常规 DSt 暂停前向请求后，StateEst 路径跑满 `65.001 s`、完成 17 次支撑切换，QP 最大基座加速度约 `13.6688`，最大等式/不等式残差约 `2.27e-13/3.07e-12`；第三次换载的异常 QP 已解决；
- 新增 23 关节实际动态审计后，65 秒速度/力矩均零越界，但 ankle-pitch 位置仍有 15655 个越界采样；最差 `left_ankle_pitch_joint=-0.562484 rad`，比 URDF 下限低 `0.028484 rad`。当时目标为 `-0.474 rad`、测得力矩为正向恢复，表明是落地/闭链冲击下的动态穿透；
- ankle-pitch 余量 `0.070 rad` 仍产生越界，`0.080 rad` 于 `19.856 s` 破坏长时稳定；提高 `kd` 和迁入限位附近前馈衰减也分别降低稳定性或把 65 秒切换数降到 8，均已撤销。D014 的控制阻塞已解除，但 P0-7 仍需解决 ankle-pitch 动态位置限位，不能通过放宽 URDF 限位完成验收。
